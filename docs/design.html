1 · Narrative

The story

Meridian Semiconductor makes analog power-management ICs — the small chips that regulate voltage inside cars, factory drives, and phone chargers. Fab 3 in Red Rock, Arizona is its back-end line: wafers arrive from the front-end fab already probed, get sawn into die, attached to lead frames, wire-bonded, inspected, molded in epoxy, tested, and shipped in reels. It runs three shifts, 24/7, and every station on the line talks to a Redpanda cluster.

Until last year the data side of the line was a collection of Spark jobs, a fleet of long-running containers, and a per-station Python script nobody wanted to touch. Four things kept paging the on-call engineer. At 06:00 and 14:00 shift changes, every prober on the floor uploads its lot summaries at once and the consumers fell over. A single malformed STDF record from a mis-calibrated prober could stall a partition for hours. When a broker restarted mid-batch, the final-test service occasionally dispositioned a lot twice, and Tape & Reel shipped against a phantom inventory count. And the X-ray inspection backlog after a wire-bond excursion took most of a shift to drain, because the inspection service was sized for a quiet Tuesday.

The platform team rebuilt the line's data path on Cosmonic. Each station is now one small Rust component, compiled to a WebAssembly component and built from one of the rust-kafka-* golden templates. The component never links librdkafka and never sees a broker address: the host's Kafka plugin owns every client, and the workload's binding grants the broker, the credential, the consumer group and the exact topics it may touch. The team put the broker and SASL credential in the host's kafka.yaml once; station manifests name only their topics and their group. A component cannot point itself at another cluster, cannot read a topic it wasn't granted, and cannot load native code on the host. Stations that do per-record work use the handler pattern — the host owns offsets, retries and the dead-letter topic, the guest instances scale with assigned partition work and return to zero between batches, and a handler can produce, so die attach publishes its out-of-spec flags without a second workload. Wire bond, which needs to seek and pause per bonder, runs as a pull service with its own commit policy. Lot disposition runs transactionally, so a replayed batch can never double-count inventory. And the two stations whose load is spiky — inspection jobs and mold-oven telemetry — run on two proposed elastic handler variants that add what the handler alone does not: growing and shrinking the replica count, and so the group membership, between a floor and a ceiling.

The line supervisor watches one dashboard. It reads left to right in the same order the product moves down the floor, one section per station, with the summary numbers, the live faults, and — for the elastic stations — the replica window drawn as a slider between min and max.

"p" = partitions. Throughput ceiling for every consumer-side station is partitions × replicas — a partition is only ever assigned to one group member — which is why the elastic ceilings equal the partition counts. Inside one handler replica, useful concurrency is min(assigned partitions, 64, poolSize × maxConcurrency); the templates ship poolSize: 32, maxConcurrency: 1.

4 · Elastic templates

Two proposed templates: work queue and stream processor

Proposed, not shipped. Desktop ships four rust-kafka-* templates. The two below are additions this demo needs; the manifest keys and export names are a proposal to react to, not something the plugin accepts today.

The shipped handler is already elastic in one dimension: within a replica, guest instances scale with assigned partition work from zero to poolSize × maxConcurrency and are reclaimed after reclaimWindowSeconds — and growing that pool creates no Kafka group member and moves no partition. What it does not do is change the number of group members. Since a replica's useful concurrency is capped at its assigned partitions, a burst across 12 partitions on a single replica gets at most 12 concurrent calls however large the pool is. The two variants keep the handler shape — the host owns the consumer, the group, the DLQ; the component exports an interface the host calls — and add a scaling block that moves replicas between a floor and a ceiling on a Kafka-side signal. The dashboard draws both dimensions: live instances inside a replica, and the replica window with its min, max and current position.

Proposed manifest shape

# workload.yaml — ST-04 inspection (the shipped handler-consumer manifest + a scaling block)
apiVersion: runtime.wasmcloud.dev/v1alpha1
kind: Workload
spec:
  hostInterfaces:
    - namespace: cosmonic
      package: kafka
      version: 0.5.0
      interfaces: [handler, producer]          # exports handler, imports producer for results
      config:
        # bootstrap.servers omitted on Desktop: inherits the kafka.yaml default (fab3-redpanda)
        broker.address.family: v4
        handler.topics: "inspect.jobs"          # the subscription
        topics: "inspect.jobs,inspect.dlq,inspect.results"   # the GRANT: subscription + DLQ + every produce target
        handler.group.id: "st04-inspect"        # required, never derived, stable across redeploys
        dead-letter.topic: "inspect.dlq"        # required
        handler.batch.size: "1"                 # one job per call → a verdict per job
        auto.offset.reset: earliest
      # secretFrom: [kafka-credentials]         # Desktop: SASL_PASSWORD → sasl.password; Control: a Secret
  components:
    - name: inspector
      image: oci.localhost:8200/apps/st04-inspect:0.1.0
      poolSize: 32                              # instances scale 0→32 with assigned partition work
      maxConcurrency: 1
      reclaimWindowSeconds: 30
      reclaimMinInstances: 0
      localResources:
        allowedHosts: []                        # the plugin dials the broker, the component does not
  scaling:                                      # PROPOSED — moves `replicas` (group members)
    min: 1
    max: 12          # never above partitions — that product is the ceiling
    metric: kafka.consumer-lag
    target: 500      # records of lag per replica before adding one
    scaleUpCooldown: 30s
    scaleDownCooldown: 120s
# workload.yaml — ST-05 mold telemetry (excerpt; proposed export)
    - namespace: cosmonic
      package: kafka
      version: 0.6.0                            # PROPOSED: the version that adds stream-handler
      interfaces: [stream-handler, producer]
      config:
        broker.address.family: v4
        handler.topics: "mold.telemetry"
        topics: "mold.telemetry,mold.dlq,mold.profile"
        handler.group.id: "st05-cure-profile"
        dead-letter.topic: "mold.dlq"
        max.poll.interval.ms: "900000"          # long windows want the poll interval, not a smaller pool
  scaling:
    min: 2
    max: 8
    metric: kafka.ingest-rate-per-replica
    target: 8000     # records/s per replica
5 · Technical demo

What we actually run

Two ways to run the same six Workload specs, because the spec is the same runtime.wasmcloud.dev/v1alpha1 schema on both hosts: on a laptop, Cosmonic Desktop (its daemon compiles in Control's plugin-kafka) with Redpanda in a container; on a cluster, Cosmonic Control 0.11 on wasmCloud 2.9 with the deploy/workload-deployment.yaml each scaffold carries. The laptop is the one we demo from. The scaffolds come from cosmonic_project_create(template="rust-kafka-<pattern>"), so the audience can watch the Builder produce a station from the same starters.

Demo script (about 12 minutes)

00:00

Quiet Tuesday

Baseline scenario on all six generators. Walk the dashboard left to right; every station's consumed count equals its produced count on /validate and every group's lag reads 0. ST-04 sits at 1 replica, ST-05 at 2; ST-02's live instances hover at 2–3 of 32 and drop to 0 when a partition goes quiet.

01:30

The binding is the whole client config

Show ST-02's manifest: no broker, no credential, no client config in the code — just handler.topics, the topics grant, handler.group.id, dead-letter.topic. Then cosmonic_workload_validate a seventh manifest that sets plugin.library.paths: refused, and the sentence names the key, never a value. Then one that grants topics without its DLQ: the bind fails permanently — Failed, no retry — with the plugin's own words.

03:00

Shift change

Switch ST-01 and ST-05 generators to shift-change. Probe uploads jump 100×; ST-01's send_batch per lot absorbs it (batches of ~25 wafers; the measured curve is ~126 records/s per caller for per-record sends and 3,300–5,000 for batches of 100), ack latency p95 stays under 50 ms. Mold telemetry doubles; ST-05's replica marker walks 2→4→6 inside its window, records/s per replica stays flat.

05:00

Poison pill, two ways

ST-02 generator emits a die record with a NaN thickness. The handler returns Err(Permanent); the record lands in dieattach.dlq with its origin topic/partition/offset as headers, the DLQ counter ticks to 1, and the partition advances. Then flip the generator to the same record against a deliberately naive build that panics: the trap counts as transient, the partition stalls for five redeliveries, then the record dead-letters. Same outcome, five backoffs later — the point of "Permanent, never panic".

06:30

Bond excursion → inspection backlog

ST-03 drift scenario sags one bonder's transducer power; NSOP alarm fires on bonder 17 and the service seeks that bonder's partition back 60 s to replay the signature onto wirebond.metrics. ST-04 generator goes to excursion (20× jobs). Lag climbs, live instances inside the single replica pin at 12 (its assigned partitions — the pool cannot help past that), the replica marker slides 1→12 against the ceiling, p95 job latency stays flat, lag drains, marker slides back to 1 after cooldown. The scale-event timeline shows the whole arc.

09:00

Restart the broker mid-batch

Restart Redpanda. Expect the gap the skill warns about: a stretch of silent no-delivery, then automatic recovery on the 10 s backoff loop — the dashboard alerts on lag, and a probe record (rpk topic produce) is what proves the pipeline is back. ST-06's transactional ledger: aborted txns 1 (txn-requires-abort honoured), duplicates 0, inventory count unchanged. The non-transactional twin's shadow ledger shows +240 phantom units. Say the line out loud: a DB write isn't covered by the transaction — which is why ST-02 sinks idempotently instead.

11:00

Rolling update

Publish a new ST-03 revision with a tighter NSOP threshold. The stable consumer.group.id is what makes the new instance resume where the old one stopped; cooperative-sticky rebalancing moves only the partitions that change hands, and the heat strip never blanks. Close on /validate: every station still consumed == produced (plus the two DLQ records, accounted for), every group's lag back to 0.

Validation we show, not describe

Every beat has a number on the page that either matches or doesn't. Per station: produced count (from the generator), consumed count (from the workload), consumer-group lag (from the broker, the way rpk group describe reports it), DLQ count, redelivery count, and for ST-06 a duplicate check computed from the ledger. For the handler stations: live instances against assigned partitions. For the elastic stations: the replica count time series overlaid on lag or ingest rate, so the audience sees cause and effect rather than a claim about it. All of it comes from the same metrics topic the dashboard reads, so there is no second instrumentation path.

7 · Skill & template recap

What the shipped skill and templates say

Repeated here so this document stands alone. Sources: the cosmonic-kafka skill (v1.2.0 — the same file in agent-integrations/core/skills and vendored into Desktop's cosmonic-mcp, apart from the version stamp), the four rust-kafka-* starters compiled into Desktop (vendored from awesome-cosmonic components/kafka @ f5326286, the cosmonic:kafka@0.5.0 set, tested live against Cosmonic Control 0.11.0 on wasmCloud 2.9), and daemon/docs/KAFKA.md.

A component on Cosmonic does not link librdkafka. It imports cosmonic:kafka@0.5.0 and the host's Kafka plugin — Control's own plugin-kafka, compiled into Desktop's daemon behind the default-on kafka feature — owns every client. The broker address, the credential, the consumer group and the topic grant live in the workload's binding; the component only ever sees producer functions, a Consumer session, a Transaction, or the batches the host hands its handler.

Hard rules

  • The guest never dials or configures Kafka. No rdkafka crate, no bootstrap.servers in code, no client config through the WIT at all: producer functions are called directly on the binding (there is no producer open, close or flush), Consumer::open() takes no arguments, transaction::begin() takes none. A component cannot redirect itself or pick a group.
  • topics is the grant; handler.topics is the subscription. The grant must contain every subscription, the dead-letter.topic, and every topic a producer/consumer/transaction call names. Absent or empty grants nothing: a handler binding without topics is refused at bind. Never * wider than needed.
  • Handlers: handler.group.id and dead-letter.topic are both required and never derived. A pull consumer's group is consumer.group.id; plain group.id is not a binding key. A transaction binding needs transactional.id and, for send-offsets, transaction.group.id.
  • Start with the handler — it can produce. A handler that imports producer beside its handler export is the elastic consume-transform-produce shape; the host reuses one binding-scoped producer across instances. Reach for the pull service only when the code needs the consumer session (assign, pause, seek, rebalance events, pull pacing, its own commits), and for transaction only when outputs and offsets must commit atomically. Never open a pull consumer per invocation: it is a stateful group member (64 per component).
  • Async-only WASI p3. Every function is an async func. Rust needs wit-bindgen ≥ 0.58 with async-spawn + inter-task-wakeup on wasm32-wasip2. TinyGo cannot bind it; there is no Go set.
  • Malformed input is Permanent, never a panic. A trap is retried like a transient error; five consecutive traps on one record dead-letter it, and until then that partition makes no progress.

The surface: five interfaces, one export

ImportGives the guest
typesconsumed-record, produce-record, produce-ack, partition-ref, partition-offset, partition-result, watermarks, error {code, message, fatal, retriable, txn-requires-abort}. Bound whenever any other interface is; needs no interfaces: entry.
producerFree functions on the binding's host-owned client — send(topic, record) → produce-ack, send-batch(topic, records) → list<result<ack, error>> (per-record outcomes), send-stream(topic, stream) → future<result>, partition-count, watermark-offsets. No open, no flush.

ExportThe host calls it forManifest keys that drive it
handler.handle(list<consumed-record>) → result<option<offset>, handler-error>each batch from ONE partition, in offset order — up to handler.batch.size (default 100, max 10000) and ~1 MiBhandler.topics, handler.group.id, dead-letter.topic, topics (must cover both), handler.batch.size, auto.offset.reset

Handler return semantics (at-least-once): Ok(None) = the whole batch handled, the host stores past its last record; Ok(Some(offset)) = handled through that record (its own offset, not the next), the host stores past it and redelivers the rest; Err(Transient) = nothing handled, rewind and redeliver (backing off 100 ms → 30 s) indefinitely; Err(Permanent) = a single-record batch goes to dead-letter.topic with the origin topic/partition/offset and the detail string as headers, and the partition advances — on a longer batch the host redelivers the first record alone so the verdict lands on one record. After a failure the loop's batch ceiling drops to one and doubles back with each success. Prefer Ok(Some(..)) over an error once any record succeeded.

Where the broker comes from

The plugin opens its connections from the daemon process — librdkafka dials the broker, not the component, so allowedHosts stays []. The plugin declares bootstrap.servers a required key on its own binding schema and wash-runtime checks it against the fully resolved binding under every policy, so every binding has its broker before the component runs, from one of two places: the manifest's own cosmonic:kafka entry (Control's model; what the templates do), or on Desktop a <state_dir>/kafka.yaml default the binding inherits. kafka.yaml is a base the workload overrides key by key; a binding with a broker from neither is refused in the plugin's own words.

# <state_dir>/kafka.yaml — Desktop's defaults (file-only, read at boot, fail-closed)
config:                          # the unnamed binding, and the base under every named one
  bootstrap.servers: 127.0.0.1:9092
  broker.address.family: v4
secret_from: [kafka-sasl-password]   # registered refs whose VALUES join that layer at boot
bindings:                        # `name: orders` on a workload's cosmonic:kafka entry
  orders:
    config:
      bootstrap.servers: kafka.internal:9093
      security.protocol: SASL_SSL
      sasl.mechanism: SCRAM-SHA-512
    secret_from: [orders-sasl-password]
  • Host-only keys are refused to a workload on every host: anything loading native code (plugin.library.paths, ssl.engine.location, ssl.providers), reading a host file by path (ssl.*.location, https.ca.location, sasl.kerberos.keytab, the sasl.oauthbearer.assertion.*.file keys), running a command or reaching a host-chosen URL (sasl.kerberos.kinit.cmd, sasl.oauthbearer.token.endpoint.url), or weakening/flooding the host (enable.ssl.certificate.verification, ssl.endpoint.identification.algorithm, debug, statistics.interval.ms). Credentials are yours: TLS material inline as ssl.ca.pem and friends through config/secretFrom, never as file paths. An operator who needs a host-only key sets it in kafka.yaml.
  • One spelling per setting. librdkafka alias pairs (metadata.broker.list = bootstrap.servers, …) are folded to one spelling per config source before the layers merge, so an alias cannot dodge a rule; an all-caps secretFrom key like SASL_PASSWORD arrives as sasl.password.
  • The machine egress allow-list. Where the enterprise machine layer sets one, every broker a binding would dial — its own or an inherited default — must be on it, matched the way allowedHosts entries match (port 9092 when an entry names none). No floor, no check.
  • Several Kafkas from one workload: one cosmonic:kafka entry per (implements <name>) label, each with its own name, broker, credential and grant. The dev loop and /v1/synthesize infer one named entry per label from the component's world.
  • A refusal at apply (host-only key, off-allow-list broker) is a 400 whose sentence names the key, never a value — cosmonic_workload_validate says the same. A refusal at bind (no broker anywhere, a grant that misses the subscription or DLQ, a missing group id) fails the start permanently: Failed, no retry; fix and re-apply. requires cosmonic:kafka which this host does not provide means a daemon built without the kafka feature.

Rules that keep it running

  • Scaling = partitions × replicas, for handlers and pull services alike. Per replica a handler's useful concurrency is min(assigned partitions, 64, poolSize × maxConcurrency); growing the pool adds no group member and moves no partition — the host keeps the native consumer, connection and membership alive while guest instances come and go. Keep maxConcurrency: 1 unless the handler is safe under overlapping calls on one instance. Add replicas for availability or more group members.
  • A slow handler wants max.poll.interval.ms, not a smaller pool. The per-call deadline derives from it (the interval less a minute — ten minutes by default) and covers the whole batch; the host serves the group's poll timer independently.
  • Rebalancing is cooperative-sticky by default; every member of a group must agree, so never mix strategies across deployments sharing a handler.group.id.
  • Throughput vs latency in a service is BATCH_SIZE. Per-record send+await is a broker round trip each (~126 records/s measured); batches of 100 move thousands per second; send-batch of ~100 → 3,300–5,000 records/s, of 500 → 30,000+. Raise it only for a steady stream.
  • Never drain an unbounded records() stream inside one request-scoped call — it stalls silently past ~10–12k records. records() is callable once per consumer, and reading it is what keeps the group heartbeat alive.
  • Read the error record, not just code: retriable says retry; fatal on the producer means the host retires the native client (a consumer must be closed and reopened); txn-requires-abort means abort the transaction and reprocess. not-leader-for-partition is "refresh metadata and retry", not "give up".
  • After a broker restart that changed its identity expect minutes of silent no-delivery, then automatic recovery (10 s backoff loop) — alert on consumer lag, send a probe record before trusting the pipeline.
  • Handler pitfalls: keeping required state in the instance (calls land on different instances; idle ones are reclaimed — package-level state is a cache, never isolation); leaving the DLQ or an output topic out of topics; a second component exporting handler in the same workload (refused — they would split one group). Measured (0.3.0 campaign, dispatch unchanged): ceiling > 11,000 records/s on one Rust component; 300 records/s soak at 6 ms median, 57 ms p99, zero loss; replicas 1 → 2 ≈ 1.6× on one node; driver trace logging raised p99 ~20×.
